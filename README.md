# 로또 아틀리에 — 1등 확률을 먼저 확인하는 조합 구성

**[로또번호 생성기.html](로또번호%20생성기.html)을 열거나 새로고침하세요.** 인터넷·엑셀·추가 설치 없이 작동합니다.

1. 구매할 회차와 만들 게임 수를 고릅니다. 기본은 최신 공식 자료의 다음 회차·**5게임**이며, 값을 바꾸면 해당 묶음이 바로 생성됩니다.
2. 번호 목록 위에서 **선택 회차 전체의 1등 확률**을 확인합니다. 같은 회차의 보관 번호와 현재 묶음을 합친 고유 조합 수, 퍼센트, ‘몇 분의 1’을 함께 표시합니다.
3. 다른 번호를 원하면 **새 번호 만들기**를 누르고, 필요한 번호를 저장·복사하거나 CSV로 받습니다.
4. 1등 계산 기준·등위별 확률, 보관함·당첨 확인은 아래의 접힌 항목을 펼쳐 확인합니다.

기본 5게임의 1등 확률은 **5 / 8,145,060 = 1,629,012분의 1 ≈ 0.00006139%**입니다. 한 번에 1~20게임을 만들며, 저장 후 같은 회차로 다시 생성하면 보관함의 기존 여섯 번호 조합과 겹치지 않는 새 묶음을 추가합니다. 화면의 큰 1등 확률은 선택 회차의 보관 번호와 현재 묶음을 모두 합쳐 중복 제거한 고유 조합 수로 계산합니다. 백분율은 소수점 이하 8자리로 반올림하고, 역수가 정수가 아닌 경우 ‘약’으로 표시합니다. 5등 이상 확률 카드는 계산 가능한 경우 같은 회차의 보관함과 현재 묶음 전체를 표시합니다. 두 게임의 공통 번호가 2개 이상이거나 전체가 20게임을 넘으면 현재 묶음만 표시하고 범위를 안내합니다.

빈도·시차·혼합 모형 선택과 고정·제외·합계·홀짝 조건을 화면에서 제거했습니다(이들은 당첨 확률을 바꾸지 못합니다). 적어도 한 게임이 당첨되는 확률을 넓히는 배치를 자동 적용합니다.

아래는 보관 번호가 없는 단독 생성의 기준입니다.

- **1~7게임:** 게임끼리 같은 번호를 사용하지 않습니다.
- **8~20게임:** 45개 번호를 고르게 쓰고, 두 게임의 공통 번호를 최대 1개로 제한합니다.
- 모든 번호를 공정한 난수로 일대일 치환합니다. 배치가 같으면 번호를 새로 섞어도 확률은 같습니다.

| 같은 게임 수 | 무작위 묶음 평균: 5등 이상 | 현재 배치: 5등 이상 |
|---:|---:|---:|
| 5 | 11.3624% | 11.8679% |
| 10 | 21.4337% | 23.0209% |
| 15 | 30.3607% | 33.4643% |
| 20 | 38.2734% | 42.6653% |

기본 5게임의 확률은 앞 버전의 완전 분산 방식과 같습니다. 2026-10-18 개선 배치는 11~14·16~20게임에 적용했습니다. 비교는 항상 **같은 게임 수**를 기준으로 합니다.

현재 배치는 **4등 이상 한 장이라도 당첨될 확률이 같은 게임 수의 수학적 상한**에 도달합니다. 단독 1~8게임의 5등 이상 확률도 전역 최적임을 증명했습니다. 9게임 이상은 전역 최적성을 보장하지 않습니다. 1등 확률은 서로 다른 m게임이면 어느 구성이나 m/8,145,060이며, 기대 당첨 장수나 수익을 늘린다는 뜻은 아닙니다. 확률은 공정·독립 추첨을 가정합니다. [동행복권 공식 규칙](https://m.dhlottery.co.kr/lt645/intro)

화면의 큰 1등 확률은 **선택한 같은 한 회차에 사용할 현재 묶음과 보관 번호 전체**의 값입니다. 새 번호는 같은 회차의 보관 조합을 강제 제외하며, 기존 자료 중 회차가 기록되지 않은 묶음은 합산하지 않습니다. 보관하지 않은 종이 복권이나 다른 기기의 번호는 알 수 없으므로 직접 합산되지 않습니다.

## 보관 번호에 맞춘 추가 생성

같은 회차로 저장한 조합은 바꾸지 않고 새 조합만 만듭니다. 사용할 번호가 충분하면 겹침 없이 배치하고, 가능한 경우 전체 게임 수의 검증된 배치에 기존 번호를 대응시켜 연결합니다. 예를 들어 비중복 5게임 저장 후 5게임을 추가하면 전체 10게임의 5등 이상 확률은 **23.020886%**입니다. 새로 추가한 5게임끼리는 일부 번호가 겹칠 수 있습니다.

기존 번호가 임의로 겹쳐 검증된 배치에 연결되지 않으면 제한된 후보를 비교합니다. 전체 확률을 정확히 계산할 수 있는 후보를 우선하고, 그렇지 않으면 겹침이 적은 후보를 고르며 전체 확률을 보장하지 않습니다. 기존 번호를 유지하는 것이 우선이므로 모든 저장 이력을 최적 배치로 확장할 수 있는 것은 아닙니다.

보관함은 기존 버전의 로컬 저장 키를 유지했습니다. 브라우저·파일 위치를 바꾸거나 브라우저 데이터를 삭제하면 기록 접근이 달라질 수 있습니다. 중요한 번호는 CSV로 보관해 주세요. 당첨번호 대조는 공식 720회부터의 저장 자료를 사용하며, 배포 사이트에서는 매주 자동 갱신됩니다(아래 ‘당첨번호 자동 갱신’). 아직 반영되지 않은 회차는 직접 입력할 수 있습니다. 과거 대조는 미래 예측 성적이 아닙니다.

## 보관함 · 당첨 확인

번호를 만든 뒤 **보관함에 저장**해 두면(같은 회차로 여러 번 나눠 저장 가능), 그 회차의 공식 당첨번호가 들어온 뒤 앱을 열었을 때 화면 맨 위에 `1243회 추첨 결과 · 보관한 10게임 — 5등 1게임 · 미당첨 9게임`처럼 요약이 나타납니다. **번호는 그 번호를 산 회차의 당첨번호와만 대조합니다.** 예전의 ‘당첨번호와 대조하기’(임의의 과거 회차와 현재 번호를 비교)와 보관함을 하나로 합쳤습니다.

- 보관함은 **회차별로 모아** 당첨번호를 한 번만 보여 주고, 그 아래에 1번째·2번째 저장 묶음을 나열합니다.
- 게임마다 맞은 본번호는 실선, 보너스 번호는 점선 테두리로 표시하고 **맨 오른쪽에 등위(1~5등·미당첨)와 일치 개수**를 적습니다.
- 같은 여섯 번호를 중복 저장한 경우 요약에서는 한 번만 셉니다. 당첨번호가 아직 없는 회차와 회차가 기록되지 않은 이전 버전 묶음은 대조하지 않습니다.
- 자동 갱신이 아직 안 된 회차는 패널 아래 **‘당첨번호가 아직 안 들어온 회차 직접 입력’**에서 회차·본번호 6개·보너스를 넣어 대조할 수 있습니다. 입력값은 이 기기에만 저장되며, 공식 자료가 들어오면 공식 번호가 우선합니다.
- 화면의 현재 번호도 선택한 회차에 당첨번호가 있으면 같은 방식으로 표시합니다.

참고용 결과이며 실제 당첨 여부와 당첨금은 복권의 QR 코드나 판매점에서 확인해야 합니다. 검사: `node --test tests/saved-results.test.cjs`.

## 오프라인 지원

배포 사이트(GitHub Pages)를 한 번 온라인으로 열면 `sw.js`(서비스 워커)가 앱 화면과 아이콘을 기기에 저장합니다. 그 뒤에는 네트워크가 없어도 앱이 열리고 번호 생성·보관함·저장된 회차 대조가 모두 동작합니다. 온라인일 때는 서버의 최신본을 먼저 확인합니다. 4초 넘게 느리면 사본으로 먼저 열고, 응답이 도착하면 다음 실행용 사본을 갱신합니다. 화면 위에 수록된 최신 회차와 **업데이트 확인** 버튼이 있습니다. 새 버전이 있으면 **새 버전 열기**로 적용하며 보관함은 유지됩니다. 배포마다 사본 버전이 바뀌고, 버전 주소로 연 새 화면도 오프라인 기본 화면에 반영합니다. 네트워크가 끊기면 최신 여부를 확인하지 못했다고 표시합니다. 파일로 직접 연 `로또번호 생성기.html`은 원래 네트워크가 필요 없으며 서비스 워커를 등록하지 않습니다. 검사: `node --test tests/sw.test.cjs`.

## 당첨번호 자동 갱신 (GitHub Actions)

`.github/workflows/update-draws.yml`이 매주 토요일 21:47·22:17·23:17(KST)과 일요일 08:17(재시도)에 `scripts/update-recent-draws.cjs`를 실행합니다. 동행복권 공식 결과 API에서 새 회차를 받아 검증(토요일·7일 간격·회차 연속·번호 범위/중복)한 뒤 `data/recent-draws.json`에 쌓고, 다시 빌드해 `docs/`(GitHub Pages)에 반영합니다. HTML 응답·통신 오류·일시적인 서버 오류는 최대 4회(5·15·30초 간격) 재시도합니다. 토요일 21:40 이후에도 예상 회차가 없으면 성공으로 처리하지 않습니다. 전체 검증 후 파일을 원자적으로 교체하므로 실패하면 기존 자료가 유지됩니다. 새 회차가 없고 최신 회차까지 확인되면 아무것도 커밋하지 않습니다. GitHub의 예약 실행은 붐비면 몇 시간씩 늦게 시작될 수 있습니다(정각·30분을 피해 설정). Actions 탭의 **Run workflow**로 수동 실행할 수 있고, PC에서는 `node scripts/update-recent-draws.cjs && node scripts/build.cjs`로 같은 작업을 합니다.

분석용 `data/draws.json`(2026-10-10 기준 720~1244회, 525회)은 자동 갱신하지 않습니다. 그 이후 회차는 앱의 **당첨번호 대조**에만 쓰이며, 보존한 연구 자료와 분석 모형은 바꾸지 않습니다. 1등 유형·시차 연구는 해시로 고정된 1241회까지의 스냅숏 `data/draws-720-1241.json`을 그대로 씁니다. 해시 검증이 어느 환경에서나 같도록 `.gitattributes`에서 줄바꿈 변환을 껐습니다.

자세한 비교, 1~20게임 수치, 고정번호·휠링 검토, 확률 상한 증명, 정확식, 탐색 범위와 한계는 **[ANALYSIS.md](ANALYSIS.md)**에 있습니다.

과거 1등 당첨 조합을 참고한 추가 연구는 **[JACKPOT_ANALYSIS.md](JACKPOT_ANALYSIS.md)**에 있습니다. 공식 522회를 10가지 방식으로 분류하고 전체 8,145,060개 조합의 유형별 개수를 정확히 세었습니다. 과거 빈도로 만든 11개 대안과 균등 기준을 순차 비교했지만 미래 1등 확률 우위는 확인하지 못했습니다. [전체 유형 통계·1242회 실험 추정 CSV](data/jackpot-exports/type-probabilities.csv)와 [522회 번호·유형 CSV](data/jackpot-exports/draw-types.csv)를 함께 제공합니다. 실험 추정은 검증된 미래 확률이 아니며 생성 방식에 예측 가중치로 적용하지 않았습니다.

이전에 사용한 인기 번호대 회피·당첨금 분할 위험 추정의 코드와 자료는 연구 기록으로 보존했습니다. 현재 앱에서는 해당 모듈과 모형을 불러오지 않으며, 번호 생성과 후보 선택에 사용하거나 예상 수령액을 표시하지 않습니다.
